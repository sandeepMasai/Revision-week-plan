1. Types of Errors in Node.js

Standard JavaScript errors: Such as <EvalError>, <SyntaxError>, <RangeError>, <ReferenceError>, and <TypeError>.
System errors: Generated by the underlying operating system (e.g., ENOENT for file not found, ECONNREFUSED for connection failure).
User-specified errors: Custom errors triggered by application logic.
Assertion errors: Triggered when Node.js detects a logic violation via the assert module. 
2. Synchronous vs. Asynchronous Error Handling 
Synchronous: Handled using try...catch blocks. If an error is thrown, the execution stops and jumps to the catch block.
Asynchronous:
Callbacks: Follow the "error-first" pattern where the first argument of the callback is the error object (err, data) => { ... }.
Promises: Handled via .catch() blocks.
Async/Await: Handled using try...catch blocks, making async code look and behave like sync code. 
3. The try-catch Block
A try-catch block is a construct used to handle exceptions. You place code that might throw an error inside try and define the recovery logic in catch. 
When to use: Use it for synchronous code and with async/await. Avoid using it inside standard node callbacks, as it won't catch errors thrown in a different phase of the event loop. 
4. Handling Unhandled Promise Rejections
If a promise is rejected without a .catch() or try-catch block, Node.js emits an unhandledRejection event. You can catch these globally to log them and gracefully shut down the process: 
javascript
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Rejection at:', promise, 'reason:', reason);
  process.exit(1);
});
Use code with caution.

5. Operational Errors vs. Programmer Errors
Operational Errors: Runtime problems where the impact is expected (e.g., "file not found," "network timeout," "invalid user input"). These should be handled gracefully.
Programmer Errors: Bugs in the code (e.g., "undefined is not a function," "trying to read property of null"). The best recovery is usually to log the error and restart the process. 
6. Centralized Error Handling in Express
This is implemented using error-handling middleware. Define a function with four arguments at the end of your middleware stack: 
javascript
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;
  res.status(status).json({ error: err.message });
});
To trigger this, pass the error to next(err) inside any route or middleware. 
7. Input Validation and Its Importance
Input validation is the process of ensuring that the data provided by the user meets the application's requirements (type, length, format). 
Importance: It prevents malformed data from crashing the app, protects against SQL injection or XSS attacks, and ensures data integrity in the database. 
8. Validation Libraries
Joi: A schema-based validator often used for validating JS objects.
express-validator: A set of express.js middlewares that wrap validator.js.
Zod: A TypeScript-first schema declaration and validation library. 
9. How to Sanitize User Input
Sanitization is the process of cleaning input to prevent security attacks (like removing HTML tags or escaping special characters). 
Use libraries like express-validator to trim whitespace or escape HTML: body('email').isEmail().normalizeEmail().
Use libraries like DOMPurify for cleaning HTML strings.
Always use parameterized queries (prepared statements) to sanitize data before database insertion. 
10. Client-side vs. Server-side Validation
Client-side: Occurs in the browser HTML5 required attribute, JavaScript It provides instant feedback for a better User Experience (UX) but can be easily bypassed by attackers.
Server-side: Occurs on the server. It is mandatory for security and data integrity because it cannot be bypassed by the user. Always validate on the server, even if you validate on the client.
